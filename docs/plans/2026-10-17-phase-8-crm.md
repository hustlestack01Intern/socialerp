# PLAN: Phase 8 — CRM memory, segments, owner insights, owner WhatsApp console

Date: 2026-10-17. Author: Chief Engineer. Classification (via @taxonomist):
type = feature delivery (new domain) + privacy-sensitive data handling;
risk = HIGH (Kenya DPA privacy zone: consent, export, erasure, PII; tenant
isolation release blocker); complexity = HIGH — split into three slices.

## Goal / non-goals

Goal: make SocialERP "smarter about its customers" per AGENTS.md §10 and §2 —
a customer database that remembers history, preferences and behaviour, turns
them into better offers/decisions, and lets the owner run the business by
chatting with the agent. Non-goals: inferred sensitive attributes (health,
religion, ethnicity, sexual orientation — FORBIDDEN), real customer data,
live messaging endpoints, LLM arithmetic.

Single-purpose test (AGENTS.md §1): every trait/segment/insight must either win
or protect a sale, save the owner time, or make the business smarter about its
customers. Nothing else is built.

## Invariants

1. **No inferred sensitive attributes.** `derive_traits` has an explicit
   allow-list of trait names; anything not on it is refused (tested).
2. **Evidence** behind every derived trait is stored (`evidence_json`) and the
   trait is **versioned** (a new computation appends a new version; prior
   versions are kept). A trait with no evidence is refused.
3. **Immutable event log.** `customer_events` is append-only (no update/delete
   path in the service). Events summarise; they never store raw message bodies
   wholesale (PII minimisation).
4. **Consent is explicit and sourced.** Marketing/win-back sends require a
   `marketing` consent record with source + time; opt-out is honoured.
5. **Deletion is human-approved** (AGENTS.md §6) and fully audited; erasure is
   tenant-scoped and irreversible-cascade for the customer's CRM data.
6. **Tenant isolation**: every table carries `tenant_id`; RLS policy + grants
   in the migration; cross-tenant tests fail closed (release blocker).
7. **Deterministic derivation**: trait arithmetic (RFM, LTV, reorder cycle) is
   plain integer/date code, never the LLM.

## Slice 8a — CRM memory (events, consent, traits, export, erasure)

- Models (`packages/core/models/crm.py`): `CustomerEvent` (append-only),
  `ConsentRecord`, `CustomerTrait` (versioned + evidence).
- Migration `0012_crm.py` (RLS + `socialerp_app` grants; mirror 0011).
- `packages/core/crm/` service + repositories:
  - `record_event(...)` — append a summarised, PII-minimal event.
  - `record_consent(...)` / `has_consent(customer, purpose)` / `opt_out(...)`.
  - `derive_traits(customer_id)` — allow-listed traits from the event log +
    orders (RFM, lifetime_value_cents, reorder_cycle_days, typical_order_hour,
    preferred_size/colour from order items), each with evidence + version.
  - `export_customer(customer_id)` — data-subject access (events + traits +
    consent + orders summary).
  - `delete_customer(customer_id)` — erasure (human-approved at the API layer).
- API (`apps/api/routes/crm.py`): list/get customers, get events, get traits,
  record consent, export, delete (owner-only, audited).
- Tests: trait derivation with evidence; sensitive-trait refusal; immutability
  (no update path); consent gating + opt-out; export completeness; erasure
  cascade; cross-tenant RLS fail-closed (non-owner role).

## Slice 8b — Segments + owner insights

- `Segment` model + deterministic rule evaluator (trait predicates, all/any).
- Insights service: daily/weekly owner report (orders, revenue, top items,
  new/returning customers, stock alerts) + simple anomaly detection (e.g.
  orders today vs trailing median). Pure code; numbers trace to the ledger.
- API + tests (segment evaluation determinism; report totals match the DB;
  anomaly fires on a synthetic spike).

## Slice 8c — Owner WhatsApp console

- Owner intents ("how many orders today?", "mark order 1042 delivered",
  "restock 20 of SKU X") parsed deterministically where possible, routed
  through the policy engine; refunds/discounts/price changes/bulk sends stay
  human-approved (protected zone). Every action audited.
- Tests: read intents answered from the DB; write intents gated; injection
  attempts blocked; non-owner phone never gets the console.

## Acceptance (Phase 8)

- `make check` green (ruff, mypy strict, pytest, evals) with real output.
- No sensitive trait can be derived (negative test).
- Every trait carries evidence + version (positive test).
- Consent required for marketing; opt-out honoured (test).
- Export returns the full subject record; erasure removes it (tests).
- Cross-tenant CRM access fails closed (RLS test through the non-owner role).
- Owner console actions audited; risky actions human-approved (tests).

## Protected zones touched

- None by mutation. The console reuses (does not modify) the payments
  protected zone; refund/discount actions remain human-approved.
- `tests/conftest.py::_RLS_TENANT_TABLES`: add the new CRM tables
  (strengthening the isolation harness — flagged in the commit).
